Chapter 1

What PlaceCell is, in one page

PlaceCell is a campus placement workspace. Three kinds of people use it:

  • Students keep a profile, browse ranked jobs, apply, upload a resume for AI scoring, and join interviews.
  • Recruiters post roles, filter applicants, shortlist or reject, edit or close a role, and book interviews.
  • Admins (the placement cell) approve jobs and read analytics snapshots.

It is not a copy of the older Express + Vercel app. It is a new NestJS system: one OS process per feature behind a path gateway, a separate worker for slow work, Redis for cache and locks, MongoDB as the source of truth, and MinIO for resume files in Docker. Mongo is shared across processes. Isolation is deployment (a down matching process cannot crash catalog), not a database per service.

The sentence to remember

The browser never talks to Mongo or Redis. It only calls /v1/.... Slow or retryable work (resume parse, email, rank refresh) is written to an outbox row, then a worker picks it up. That is why resume upload returns 202 Accepted instead of waiting for the LLM.

One process per feature (microservices by path)

There is one Node codebase. At runtime, SERVICE=identity|catalog|… loads only that Nest module. JWT verify is shared (AuthCoreModule). Mongo is still one cluster — isolation is process-level, so if matching dies, jobs and apply still work.

Why split processes, not databases? The assignment needed “if a feature goes down the rest of the site still works.” Path-based services give that without seven Mongo clusters. The UI uses apiTry() so a 503 does not blank the page.

Docker Compose layout

docker-compose.yml starts Mongo, Redis, MinIO (resume bucket), the seven feature containers, the worker, and nginx which both serves the SPA and routes /v1/… by prefix. Host ports: app 8080, Mongo 27018 (database placecell), Redis 6380, MinIO console 9001. Homebrew Mongo on 27017 / database nexus is left alone so Compass still shows local npm data.

Commands: npm run docker:up, then npm run docker:seed. Open http://localhost:8080.

Consistency choices (the CAP note from your study pages)

  • Apply and interview booking are CP-ish. Unique index on student+job. Idempotency key. Redis SET NX lock on an interview slot. We would rather fail a double-book than invent a second interview.
  • Job feed and inbox are AP-ish. Rank cache lives 1 hour. A slightly stale score is acceptable. Inbox can poll.

Chapter 3

How a request travels

This is the path of almost every click.

Figure 3. Request flowchart. Refresh happens only when the 15-minute access token is stale.

  1. React calls api("/v1/...") in client/src/utils/api.ts.
  2. That helper attaches Authorization: Bearer … from sessionStorage.placecell_access.
  3. If the access token expired (15 minutes), it posts /v1/auth/refresh with the httpOnly cookie, stores the new access token, and retries once.
  4. Nest global ThrottlerGuard allows 120 calls / minute / client (stricter on AI ask).
  5. JwtAuthGuard reads the bearer token. RolesGuard checks @Roles("student") etc.
  6. The service talks to Mongo (and sometimes Redis). Writes that need follow-up call outbox.emit(eventType, payload).
  7. JSON comes back. The page updates.

ObjectId vs string (a bug we actually hit)

Nest @Prop({ type: Types.ObjectId }) does not always cast. Early writes stored studentId as a string. Queries with a real ObjectId then returned empty lists — “Already applied” but the student table was blank. We now write with oid(), query with idMatch() (string or ObjectId), and use Schema.Types.ObjectId on refs.

Chapter 5

Feature: Identity and sessions

What you see

Sign in, sign up (student / recruiter / admin+code), forgot password, reset password. After login you land on the dashboard for your role.

Why it exists

Every other feature is permission-gated. A student must not list another student’s applications. An admin signup without the campus code must fail.

How it works

Figure 5. Identity flowchart. Forgot-password always looks successful so emails cannot be probed.

  1. Password is hashed with bcrypt (cost 10). We never store the raw password.
  2. Login writes a LoginEvent (who, when, IP, user agent).
  3. We issue a short access JWT (15 minutes, kept in sessionStorage) and a longer refresh token (7 days, httpOnly cookie, stored hashed in Mongo).
  4. Refresh is rotation: the old session row is revoked, a new cookie is set. Stolen cookies can be revoked.
  5. Forgot-password creates a SHA-256 hashed token, 1 hour TTL, single use. The HTTP response is always success-shaped so attackers cannot probe which emails exist.
  6. Admin signup requires ADMIN_SIGNUP_CODE.
  7. Creating a student also creates an empty StudentProfile.

Where to look

server/src/identity/ · client/src/pages/AuthPage.tsx · client/src/context/AuthContext.tsx

Chapter 6

Feature: Student profile and job catalog

What you see

On the student home: skills, expected CTC, years of experience, bio, Save, Auto-fill. Below that, recommended roles with a match percent. Recruiters post a job (needs admin approval). Admins approve from their dashboard. Recruiters can later edit fields, close, or reopen.

Why it exists

Matching needs a profile. Students must only see approved + active jobs. A recruiter must not silently publish to the campus feed — the placement cell approves first.

How job listing works

Figure 6. Catalog flowchart. Students never see a job until an admin approves it. Redis is a speed-up, not the source of truth.

  1. Recruiter POST /v1/jobs → approved: false, status: "active".
  2. Admin POST /v1/admin/jobs/:id/approve → students can see it. Event job.approved notifies the recruiter.
  3. Student GET /v1/jobs first looks in Redis sorted set jobs:rank:<userId>. If that cache is warm, jobs come back already sorted with matchScore.
  4. If the cache is empty, Mongo returns the approved active list (unranked until the worker runs).
  5. A missing ?page= used to become NaN and slice the ranked list to nothing. We now default page to 1. That is why jobs vanished after ranks warmed, then came back.

How edit / close / reopen works

  • Edit: PUT /v1/jobs/:id — only the poster, all listing fields.
  • Close: DELETE /v1/jobs/:id — sets status: "closed". Students can no longer apply. The row is not deleted.
  • Reopen: POST /v1/jobs/:id/reopen — back to active.

Where to look

server/src/catalog/ · client/src/pages/StudentDashboard.tsx · RecruiterDashboard.tsx · JobDetailPage.tsx · AdminDashboard.tsx

Chapter 7

Feature: Apply and the hiring desk

What you see

Student: Apply on a card or job detail. The button becomes Applied. The applications table shows role, company, status, match %, date, pagination. KPIs count applications and shortlist/interview.

Recruiter: Job pills with applicant counts. Filters (name, status, min match, skill, sort). Per-row Shortlist / Schedule / Reject. Bulk actions. KPIs for roles and applicants.

Why it exists

This is the marketplace. Double-apply must be impossible. Recruiters need the same filters the older portal had.

How apply works (read slowly)

Figure 7. Apply and hiring-desk flowchart. Replay on idempotency is a success, not an error.

  1. Student POST /v1/applications with { jobId } and header Idempotency-Key: job-<id>.
  2. Job must exist, be approved, and be active. Otherwise 404.
  3. If that idempotency key already exists, we return the old row (replay). Same if student+job already exists. The UI treats that as success and reloads.
  4. Otherwise we score with calculateMatchScore (skills 70 / experience 20 / salary 10) against the profile, insert the application as pending, upsert a MatchScore, emit application.applied.
  5. Worker notifies the recruiter and refreshes Redis ranks.

How recruiter listing works

GET /v1/applications/job/:jobId is the hiring table. It populates student name/email, joins StudentProfile for skill filter, then search / status / min match / sort / page in memory (campus-sized lists).

Status changes: PUT /v1/applications/:id/status or POST /v1/applications/bulk-status. Allowed values: pending, shortlisted, rejected, interview. Scheduling an interview also sets status to interview.

Statuses are a pipeline, not a chat. pending → shortlisted or rejected. Schedule moves the row to interview. The student table and inbox both read this one field. There is no second “hidden” status.

Where to look

server/src/applications/ · student and recruiter dashboards · ScheduleInterviewModal.tsx

Chapter 8

Feature: Matching and resume intelligence

What you see

Upload PDF/DOCX. Status walks: queued → parsing → scoring → analyzed (or failed with an error). Version chips. Extracted skills. Company-fit cards with five factor bars. Job-fit list. Compare last two versions. Ask-the-assistant + Clear chat.

Before any resume is analyzed, the same page still shows company/job scores from the live profile (source = profile). After analysis, source = resume and bars appear.

Two scoring formulas

Live apply / job rankResume AI (enhanced)
Skills70%55%
Experience20%20%
Salary overlap10%10%
Education—10%
Projects—5%
FunctioncalculateMatchScorecalculateEnhancedMatchScore

Skill score = matched required skills / required skills. Experience is 100 if the student meets min years, otherwise a fraction. Salary is 100 if expected CTC sits inside the band.

How upload works

Figure 8. Resume flowchart. The API returns 202 immediately. Everything after the green outbox box is the worker.

  1. POST /v1/resumes (multipart field name resume). Only PDF or DOCX, 10 MB. Returns 202 with { id, status: "uploaded", version }.
  2. File is stored under <userId>/<timestamp>-filename (disk or S3/MinIO).
  3. Outbox event resume.uploaded.
  4. Worker: status parsing → extract text (pdf-parse or mammoth) → LLM JSON extract at temperature 0.1, or regex skill bank if the LLM is down → status extracted.
  5. Score every approved active job with the enhanced formula. Company fit = best job per company. Save ResumeAnalysis. Merge skills/education/projects into the profile. Status analyzed. Notify the student. Recompute Redis ranks.

Hand-made broken PDFs fail with a parse error (we saw bad XRef entry). A real Word .docx works. Ollama health is shown as “AI ready” vs “AI fallback”.

AI chat

POST /v1/ai/ask sends the latest extracted resume + top job fits as context. The model is told to answer only from that. Rate limited (20/day). DELETE /v1/ai/chat clears history.

Where to look

server/src/matching/ · match-algorithm.ts · resume-parser.ts · worker handleResume · client/src/pages/ResumeIntelligence.tsx

Chapter 9

Feature: Interviews

What you see

Recruiter opens Schedule on an applicant: date, time, duration, video/online/in-person, meeting link, location, notes. The hiring desk and student home show upcoming interviews. Join opens the link. Add to calendar downloads an .ics file. Recruiters can reschedule, cancel, or complete on /interviews.

Why it exists

Campus drives fail when two interviews overlap for the same student, or when nobody gets a calendar file.

How booking works

Figure 9. Interview flowchart. We fail a double-book rather than invent a second slot.

  1. POST /v1/interviews with applicationId and scheduledAt (must be in the future).
  2. Only the job’s recruiter can book.
  3. Redis lock lock:interview:<studentId>:<isoTime> for 15 seconds so two clicks cannot race.
  4. We also scan that student’s other scheduled interviews and reject overlapping windows (duration vs duration).
  5. One interview per application (unique applicationId).
  6. Application status becomes interview.
  7. Event interview.scheduled → inbox for student and recruiter + optional email with ICS attached.

Calendar download uses a short JWT in the query string so the .ics link works from a mail client without the SPA session.

Where to look

server/src/interviews/ · conflict.ts · ics.ts · ScheduleInterviewModal.tsx · InterviewsPage.tsx

Chapter 10

Feature: Notifications and inbox

What you see

Bell in the shell. Unread count. Each row has a title, body, and link (student dashboard, recruiter desk, interviews, resume page). Mark all.

How it works

Figure 10. Notification flowchart. Mongo is the inbox. Redis is only a hint. Polling is the everyday path.

Anything important writes a notifications document and publishes JSON on Redis channel notify:<userId>. The client polls GET /v1/notifications (and can subscribe in full-server deploys). Serverless hosts cannot keep a socket open — polling is the fallback, same idea as the old Vercel portal.

Chapter 11

Feature: Admin analytics

What you see

Student count, application count, placement rate, average package, pending job approvals, a 12-month applications chart.

How it works — and a honesty note

Figure 11. Analytics flowchart. The dashboard must not recount every application on every load.

GET /v1/admin/analytics reads a snapshot document keyed latest. If none exists it computes on the fly. The worker can roll up on analytics.rollup. The UI subtitle says these are snapshot reads, not live scans. That is intentional: admin dashboards should not recount every application on every page load.

“Placement rate” here counts applications that reached shortlisted or interview — a campus proxy, not “offer letter signed”.

Where to look

Chapter 12

The worker and the outbox

This is the part that matches your “backend engineer” notes more than a simple CRUD app.

The problem

If login waited for rank recompute, or apply waited for email, the API would feel broken whenever Ollama or SMTP is slow. If we only pushed to Redis, a Redis blip would lose the “please analyze this resume” message.

The pattern

Figure 12. Outbox flowchart. The API never waits for Ollama or SMTP.

Event names are in server/src/common/types.ts: application.applied, application.status, job.approved, job.changed, profile.updated, resume.uploaded, interview events, analytics.rollup.

Pluggable sides

  • LLM: LLM_PROVIDER=ollama, anthropic, or regex (Compose demo — scores resumes without Ollama).
  • Storage: STORAGE_BACKEND=disk or s3 (MinIO / R2 / S3).
  • Mail: SMTP if set, otherwise printed to the server log.

You must run the worker in a second terminal. Without it, uploads stay uploaded forever and ranks stay cold.

Chapter 14

How to run a demo yourself

Local npm (Mongo :27017 / nexus)

  1. Mongo on 127.0.0.1:27017, Redis on 6379.
  2. cp server/.env.example server/.env if needed.
  3. npm install then npm run seed (optional; wipes demo collections) then npm run dev.
  4. Open http://localhost:5173. Vite proxies /v1 to the Node gateway on :5050.

Docker Compose (Mongo :27018 / placecell)

  1. Start Docker Desktop. Copy .env.example to .env and set JWT_SECRET (Compose will not start without it).
  2. npm run docker:up then npm run docker:seed. For API hot reload, npm run docker:dev bind-mounts server/src and runs tsx watch; keep the evaluation build as the default.
  3. Open http://localhost:8080. Nginx serves the SPA and routes each /v1 prefix to one container. Resume scoring uses LLM_PROVIDER=regex so Ollama is not required.
  4. Compass: connect to mongodb://127.0.0.1:27018, database placecell, collection users.

Sign in as student → Jobs, Resume, Interviews. Recruiter → Hiring. Admin → approvals and analytics. Demo password for all three seed users: Password@123.

Health

Local and Docker use the same Node gateway map: GET /health lists each feature process (true/false). GET /ready is 200 only if identity and catalog answer. In Compose, nginx proxies those two paths to the gateway container — it does not return a fake 200. A feature’s own /ready still checks Mongo and Redis.

What this system is, and is not

Is: path-routed feature processes, a worker, cache, locks, idempotent apply, hashed passwords, pluggable AI/storage, Docker Compose, and role-based UIs for student, recruiter, and admin.

Is not: a CDN + Kafka + multi-region design, or a database per service. Isolation is one Nest process per feature sharing Mongo.
